# AGENTS.md

## Project

This repository contains a WordPress plugin named **Glyphwell - Visual Equation Editor**.

The plugin adds:

1. A standalone block editor block named `glyphwell/equation`.
2. An inline equation rich-text format named `glyphwell/inline-equation`.
3. A MathLive-powered WYSIWYG math editor.
4. A tabbed symbol palette organized by math topic, including a Matrix builder.
5. KaTeX as the single equation renderer on every surface (editor preview,
   standalone block, and inline equations), using locally bundled KaTeX assets.
6. Full internationalization (i18n) with a `.pot` template and script
   translations.

## Minimum platform requirements

- WordPress: 6.0+
- PHP: 8.0+
- Node: current LTS-compatible version
- Build system: npm + webpack through `@wordpress/scripts`

`Domain Path: /languages`. JS strings are wired with `wp_set_script_translations()` in

## Core product requirements

### Standalone Equation block

Create a block named:

```text
glyphwell/equation
```

The block must:

- Appear in the block inserter as **Equation**.
- Use MathLive for WYSIWYG math editing.
- Store LaTeX as the editable source.
- Generate and store MathML from the LaTeX.
- Support left, center, and right text alignment.
- Use a custom toolbar control for alignment.
- Disable raw HTML editing for the block.
- Remain separate from WordPress core’s Math block.
- Not create transforms to or from `core/math` in the first release.
- Not support equation numbering, labels, or cross-references in the first release.
- Not support custom macros in the first release.

Recommended block attributes:

```json
{
  "latex": {
    "type": "string",
    "source": "attribute",
    "selector": "math",
    "attribute": "data-glyphwell-latex",
    "default": ""
  },
  "mathML": {
    "type": "string",
    "default": ""
  },
  "textAlign": {
    "type": "string",
    "enum": ["left", "center", "right"],
    "default": "center"
  }
}
```

`latex` is sourced from the saved `data-glyphwell-latex` HTML attribute rather
than the block comment, because WordPress runs KSES over comment attributes for
users without `unfiltered_html`, which would mangle LaTeX such as `<` and `&`.

### Inline equation formatting

Create a rich-text inline format named:

```text
glyphwell/inline-equation
```

The inline equation format must:

- Be available in rich text fields such as Paragraph, Heading, List, and Table cells.
- Use a toolbar button labeled **Equation**.
- Open a popover containing the same MathLive editor and symbol palette used by the standalone block.
- Store LaTeX in a data attribute.
- Store generated MathML as the inline object’s inner HTML.
- Behave like a single inline equation token as much as possible.
- Remain separate from WordPress core’s Math format.

Recommended inline markup:

```html
<math
  class="glyphwell-inline"
  data-glyphwell-latex="x^2 + y^2 = z^2"
  display="inline"
>
  <!-- generated MathML children -->
</math>
```

### Math source and output rules

LaTeX is always the editable source.

MathML is always generated output.

The editor must update both `latex` and `mathML` whenever the equation changes.

Generate MathML with KaTeX (`output: 'mathml'`), not MathLive, using
`latexToMathML()` in `src/utils/mathml.js`. The saved page HTML is also consumed
outside WordPress, where KaTeX is not available, so the stored MathML must
match the KaTeX rendering as closely as possible. MathLive is used only for
editing. Store the MathML as a snapshot taken when the equation is applied;
never regenerate it in `save()`, or KaTeX upgrades would invalidate saved blocks.

Do not add custom macro support in the first release.

## Rendering strategy

KaTeX is the single renderer for every surface — the editor preview, the
standalone block, and inline equations — regardless of the WordPress version or
whether the core math block is available. Equations are always rendered from the
saved LaTeX, so any styling captured in the LaTeX (e.g. `\textcolor`,
`\colorbox`) carries through to the published page.

- Enqueue the locally bundled KaTeX assets on any post that contains saved
  equation markup (detected by class plus the `data-glyphwell-latex`
  attribute); do not load them on pages without equations.
- Render standalone block equations and inline equations from the
  `data-glyphwell-latex` attribute (read in JS as `dataset.glyphwellLatex`).
- The editor preview renders the same LaTeX with the same KaTeX options so it
  matches the frontend exactly.
- Use targeted rendering only. Do not use KaTeX auto-render across the full page.

Render targets:

```text
.glyphwell__fallback
.glyphwell__mathml[data-glyphwell-latex]
.glyphwell-inline[data-glyphwell-latex]
```

The saved markup also includes KaTeX-generated MathML so the equation still
displays where KaTeX is not available (for example, when the page HTML is used
outside WordPress); on the site, KaTeX renders over it from the LaTeX.

The editor preview, the stored MathML, and the frontend renderer share one set
of options, `KATEX_OPTIONS` in `src/utils/katex-options.js`:

```js
{
  displayMode: true or false,
  throwOnError: false,
  output: 'htmlAndMathml',
  trust: false,
  maxSize: 20,
  maxExpand: 1000
}
```

## Security requirements

Any user who can edit a post or custom post type can create equations.

Do not add extra capability checks for equation authoring.

Do not rely on `unfiltered_html`.

All output must be escaped or sanitized.

Required escaping and sanitization:

- Escape LaTeX in HTML attributes with `esc_attr()`.
- Escape fallback text with `esc_html()`.
- Sanitize MathML with `wp_kses()`.
- Add a MathML-specific KSES allowlist.
- Add a KSES allowlist for the plugin’s inline equation attributes.
- Do not allow event handler attributes.
- Do not allow `script`, `style`, `href`, `src`, or external resource attributes in MathML.
- Allow the size, spacing, color, and line attributes KaTeX emits in MathML
  (`width`, `height`, `depth`, `lspace`, `rspace`, `voffset`, `maxsize`,
  `minsize`, `mathsize`, `linethickness`, `columnspacing`, `rowspacing`,
  `columnlines`, `rowlines`, `notation`, `linebreak`, `mathcolor`,
  `mathbackground`) only with validated values: lengths capped at KaTeX's
  `maxSize` of 20em, plain colors, and known keywords
  (`glyphwell_is_safe_mathml_attribute_value()`). Anything else is dropped.
- Sanitize equation `<math>` markup again at render time through the
  `render_block` filter, so stored MathML is never output raw.
- Use KaTeX with `trust: false`.

Create sanitization helpers in:

```text
includes/sanitization.php
```

Required helper functions:

```php
glyphwell_allowed_mathml_tags()
glyphwell_sanitize_mathml( string $mathml ): string
glyphwell_is_safe_mathml_attribute_value( string $name, string $value ): bool
glyphwell_sanitize_equation_markup( string $content ): string
glyphwell_extend_allowed_post_tags( array $tags, string $context ): array
```

`glyphwell_filter_rendered_block()` hooks `glyphwell_sanitize_equation_markup()`
onto `render_block`, which covers both the standalone block and inline
equations inside any rich-text block.

## Symbol palette requirements

The symbol palette is organized by math topic so symbols are easy to find for
authors who are not LaTeX experts. Symbols are grouped into the tabs listed
below; within a tab, entries must be unique (no duplicate glyph/LaTeX) and kept
in a sensible reading order.

Create symbol data in:

```text
src/data/symbols.js
```

Use a data-driven structure. The data is layout-agnostic: each glyph group is a
flat, ordered `symbols` list. How many symbols appear per visual row is decided by
CSS (the palette grid wraps to fit the popover width), not by this data. The
Matrix group is special-cased: it has no `symbols` list and instead carries
`type: 'matrix'`, which `SymbolPalette` renders as the interactive matrix builder
(see "Matrix builder" below).

Recommended shape:

```js
export const SYMBOL_GROUPS = [
  {
    id: 'basic',
    label: 'Basic',
    symbols: [
      {
        id: 'subscript',
        visual: 'x□',
        latex: 'x_{#0}',
        ariaLabel: 'Insert subscript',
      },
    ],
  },
];
```

The same symbol palette component must be reused by:

- the standalone equation block
- the inline equation popover

Groups, in this exact order (index 0 is the default-selected tab):

1. `basic` — Basic — structures and everyday arithmetic
2. `greek` — Greek — lowercase, variants, then uppercase
3. `operators` — Operators — binary operators plus calculus (derivatives, big
   operators, limits, infinity)
4. `relations` — Relations & Sets — comparison/order relations, number sets,
   membership, subsets, quantifiers, and logical connectives
5. `arrows` — Arrows
6. `symbols` — Symbols — delimiters (brackets, braces, fences), named constants,
   and decorative glyphs
7. `matrix` — Matrix — the matrix builder (`type: 'matrix'`, no `symbols` list)

When a symbol has multiple valid LaTeX aliases, choose the standard KaTeX-supported macro that renders the intended glyph.

### Matrix builder

The Matrix group is rendered by `src/components/MatrixPanel.js` (data in
`src/data/matrix.js`) whenever the active group's `type === 'matrix'`. It provides:

- A size grid (up to `MATRIX_MAX_SIZE`, currently 5×5) that inserts LaTeX via
  `buildMatrixLatex(rows, cols)` (a `pmatrix` environment).
- `BORDER_OPTIONS` — parentheses, brackets, braces, bars, etc. — applied through
  the MathLive `setEnvironment` command.
- `MATRIX_ACTIONS` — add/remove rows and columns, mapped to MathLive commands
  (`addRowBefore`, `addRowAfter`, `addColumnBefore`, `addColumnAfter`,
  `removeRow`, `removeColumn`); delete actions are flagged `destructive`.

The panel drives the editor through `onInsertLatex` / `onRunCommand`, which
`EquationPopover` forwards to `MathFieldControl`'s imperative handle.

## Editor CSS requirements

Use SCSS for editor UI styling.

Editor styles should cover:

- symbol palette tabs
- symbol buttons
- popovers
- editor layout
- preview wrappers

Do not save editor-only styling classes into post content.

Frontend markup must use stable plugin classes, for example:

```text
glyphwell-equation
glyphwell-inline
glyphwell__fallback
glyphwell__mathml
```

These class names, the block name, and the `data-glyphwell-latex` attribute
are defined once in `src/constants.js` and mirrored in `includes/constants.php`.
The two files must stay in sync — the JS emits the markup and the PHP detects and
sanitizes it.

## Asset loading rules

Editor:

- Load MathLive only in the block editor.
- Load the symbol palette only in editor contexts.
- Load editor CSS only in editor contexts.

Frontend:

- Register the KaTeX renderer assets on `init`.
- Enqueue them only on posts that actually contain equation markup.
- Detect equation blocks with `has_block( 'glyphwell/equation' )` (plus
  legacy `glyphwell__mathml` markup) and inline equations by scanning post
  content for `glyphwell-inline` together with the
  `data-glyphwell-latex` attribute.
